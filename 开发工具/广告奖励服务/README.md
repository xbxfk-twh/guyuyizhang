# 原生广告奖励收据：本地试验

目前只实现并验证了SQLite结算模块，没有HTTP服务，没有部署到生产，也没有接入游戏钱包。测试使用临时数据库和随机测试密钥。

`RewardLedger.create()`的调用方必须先验证账号会话，再传入服务端解析的64位账号索引；格式校验不是登录认证，不能直接接受客户端传来的账号ID。未来应复用经过验证的账号体系，不能拿安装随机ID冒充跨设备账号。

模块按当前[TapADN S2S文档](https://ssp.dirichlet.cn/docs/dirichlet-sdk/sdk-guide/)实现回调签名核验，绑定服务端发出的观看nonce、账号和广告位，交易号唯一去重；每日最多5笔成功收据，每笔3至6点。SQLite事务结算，失败回滚；同请求重试或重复回调返回原收据，账号可在断线后取回收据。它不会直接修改玩家的本地钱包。

未完成请求10分钟后过期，跨日不接受未结算回调；已结算交易号保留用于防重放，达到10万条总配额时拒绝新增，不通过删除有效防重记录伪装为无限轻量。上线前仍需根据真实规模制定可验证的归档/退役策略。

本地测试：

```powershell
node 回归测试/native-ad-receipt.test.js
```

此入口已纳入核心回归。测试涵盖签名、所有权、期限、每日限次、重启、并发、重复交易和写盘失败。

上线前必须补齐：真实账号认证与HTTP入口、平台S2S配置和真实回调联调、客户端按固定收据ID入钱包、网络失败重试，以及既有备份恢复下的去重。SDK Media Key与服务端S2S Security Key用途不同，不能混用；本目录不存储任何真实密钥。
